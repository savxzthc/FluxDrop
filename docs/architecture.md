# FluxDrop Architecture

FluxDrop has three parts: a Tauri desktop shell, a Rust backend, and mobile browser pages served by the PC. The desktop shell renders the React UI and talks to Rust through Tauri IPC. The Rust backend owns file validation, token generation, LAN address selection, the Axum servers, TLS material, and transfer state. The mobile pages are generated by the Rust server.

## Tauri IPC

The frontend calls explicit Tauri commands such as `create_share`, `cancel_share`, and `get_share_status`. Commands validate inputs before mutating state and return user-readable errors. Rust emits lifecycle events such as `phone_connected`, `download_started`, `progress_updated`, and `download_completed`; the React UI listens to those events and also polls status as a fallback.

## Axum Local Servers

When a transfer starts, FluxDrop detects private LAN addresses, chooses a port, and starts a rustls-backed HTTPS Axum server bound to that address. A second HTTP listener serves only generic certificate-onboarding instructions. Both receive a coordinated shutdown signal, while only the HTTPS router receives application state or exposes token-bearing routes.

The self-signed certificate contains the selected LAN IP as a subject alternative name. It is persisted in the app configuration directory and regenerated when the selected IP changes.

## Share Session Lifecycle

The active share lives in memory as `Option<ShareSession>`. Its state includes `Ready`, `AwaitingApproval`, `Approved`, `Denied`, `Downloading`, `Completed`, `Expired`, `Cancelled`, and `Error`. Approval has a 60-second deadline. A background Tokio task expires share links, and manual cancellation marks the session cancelled immediately.

## Transfer History

Terminal send and receive states are copied into a bounded JSON history log in the app configuration directory. Records are keyed by transfer session UUID to prevent duplicate terminal events. Public Tauri responses contain display metadata only; local source and destination paths used by repeat actions remain in the Rust backend. Repeating a record validates those paths and creates a fresh session with a new token and the current security settings.

## File Streaming

Single files stream from disk with Tokio async file I/O. Multi-file and folder shares are written into a bounded-memory ZIP stream without a temporary archive. Receive-mode uploads stream into randomized same-directory temporary files and are persisted without clobbering only after validation and completion. Progress events are throttled to avoid noisy UI updates.

## Token Design

Tokens are generated from 20 random bytes and encoded with unpadded base64url. This gives 160 bits of entropy and avoids UUID structure, sequential IDs, or predictable values. Tokens are stored only in memory and are single-use by default.

## Mobile Page

The QR opens a generic HTTP `/connect` page. The secure destination is held in the URL fragment, which is not sent in the HTTP request. Same-origin JavaScript validates the HTTPS destination before showing the continue action. Download pages use inline CSS and no scripts; upload pages load one immutable same-origin script. There are no fonts, CDN assets, or analytics.

## Why File Paths Are Never In URLs

HTTPS transfer routes only accept random tokens. Selected paths are canonicalized at share creation and kept in memory, so URL manipulation cannot traverse directories or request arbitrary local files.

## Event Flow

```text
User drops file
    -> Frontend calls create_share(path)
    -> Tauri command validates file
    -> Server starts if not running
    -> Token generated
    -> Share session created
    -> Server emits share_created event
    -> Frontend receives event, displays QR

Phone scans QR
    -> Phone opens generic HTTP /connect page with secure URL in fragment
    -> User accepts the self-signed certificate warning
    -> Phone requests HTTPS GET /d/:token
    -> Server validates token
    -> Server emits approval_requested event
    -> Desktop displays phone IP and file details
    -> User approves or denies

Phone taps Download
    -> Phone requests HTTPS GET /download/:token
    -> Server validates token and approval
    -> Server emits download_started event
    -> File streamed from disk
    -> Progress events emitted every 150ms
    -> On completion: download_completed emitted
    -> Token expired (single-use)
    -> Frontend shows Completed
```

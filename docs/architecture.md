# FluxDrop Architecture

FluxDrop has three parts: a Tauri desktop shell, a Rust backend, and a mobile browser page served by the PC. The desktop shell renders the React UI and talks to Rust through Tauri IPC. The Rust backend owns file validation, token generation, LAN address selection, the Axum HTTP server, and transfer state. The mobile page is self-contained HTML generated by the Rust server.

## Tauri IPC

The frontend calls explicit Tauri commands such as `create_share`, `cancel_share`, and `get_share_status`. Commands validate inputs before mutating state and return user-readable errors. Rust emits lifecycle events such as `phone_connected`, `download_started`, `progress_updated`, and `download_completed`; the React UI listens to those events and also polls status as a fallback.

## Axum Local Server

When a file is selected, FluxDrop detects private LAN addresses, chooses a port, and starts an Axum server bound to that address. The server receives a clone of shared application state, protected by Tokio locks. Routes validate tokens against the in-memory share session and never use request paths as filesystem paths.

## Share Session Lifecycle

The active share lives in memory as `Option<ShareSession>`. Its state moves through `Preparing`, `Ready`, `PhoneConnected`, `Downloading`, `Completed`, `Expired`, `Cancelled`, or `Error`. A background Tokio task wakes every 30 seconds and expires timed-out shares. Manual cancellation marks the session cancelled immediately.

## File Streaming

Downloads stream from disk with Tokio async file I/O in 64 KB chunks. FluxDrop does not read the full file into memory, which keeps behavior predictable for large files. Progress events are throttled to avoid noisy UI updates.

## Token Design

Tokens are generated from 20 random bytes and encoded with unpadded base64url. This gives 160 bits of entropy and avoids UUID structure, sequential IDs, or predictable values. Tokens are stored only in memory and are single-use by default.

## Mobile Page

The `/d/:token` page is a fully self-contained HTML document with inline CSS and no scripts, fonts, CDN assets, or analytics. Dynamic values are HTML-escaped before rendering. The browser is sufficient because the phone only needs to perform a normal HTTP download.

## Why File Paths Are Never In URLs

HTTP routes only accept random tokens. The selected file path is canonicalized at share creation and kept in memory, so URL manipulation cannot traverse directories or request arbitrary local files.

## Event Flow

```text
User drops file
    -> Frontend calls create_share(path)
    -> Tauri command validates file
    -> Server starts if not running
    -> Token generated
    -> Share session created
    -> Server emits share_created event
    -> Frontend receives event, displays QR

Phone scans QR
    -> Phone requests GET /d/:token
    -> Server validates token
    -> Server emits phone_connected event
    -> Frontend updates to PhoneConnected status
    -> Mobile page served

Phone taps Download
    -> Phone requests GET /download/:token
    -> Server validates token
    -> Server emits download_started event
    -> File streamed from disk
    -> Progress events emitted every 150ms
    -> On completion: download_completed emitted
    -> Token expired (single-use)
    -> Frontend shows Completed
```

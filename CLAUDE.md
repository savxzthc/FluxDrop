## What FluxDrop Is

A Windows desktop app (Tauri 2 + React 19 frontend, Rust backend) that sends files/folders from a PC to a phone over local Wi-Fi via a QR code. No app, account, or cloud: the PC runs a temporary local HTTPS server, the phone opens the link in a normal browser, and the payload streams directly between devices. There is also a Receive mode (phone-to-PC upload to a PC-chosen folder).

A separate marketing **website** lives in `website/` and builds independently from the app.

## Commands

All commands assume a Windows dev environment (the app only targets Windows). Run frontend commands from the repo root; Rust commands from `src-tauri/`.

### App development & build
```powershell
npm install
npm run tauri dev          # run full desktop app (frontend + Rust)
npm run dev                # frontend-only Vite dev server (port 1420)
npm run build              # tsc typecheck + vite build of the frontend
npm run tauri build        # produce Windows installers
```

### Required checks before a PR (mirror CI)
```powershell
# Rust (from src-tauri/)
cargo fmt --check
cargo clippy -- -D warnings   # warnings are errors
cargo test
cargo audit                   # requires: cargo install cargo-audit

# Frontend (from root)
npm run build
npm audit --audit-level=high
npm run release:check         # asserts version parity across 3 manifests
```

### Run a single Rust test
```powershell
cd src-tauri
cargo test <test_name>                  # by name substring
cargo test file_utils::tests            # a module's tests
```
Rust tests are inline `#[cfg(test)] mod tests` blocks inside the module under test (e.g. `file_utils.rs`, `archive.rs`). There is no JS/TS test suite — the frontend is validated by `tsc` via `npm run build`.

### Website
```powershell
npm run site:dev             # website dev server (port 4173)
npm run site:build           # output to site-dist/
npm run site:preview:secure  # serve with production headers on 127.0.0.1:8766
npm run site:audit           # audit the built site
```

## Architecture

Three layers (see `docs/architecture.md` and `docs/protocol.md` for the authoritative detail):

1. **React frontend** (`src/`) — renders the UI and calls Rust via Tauri IPC.
2. **Rust backend** (`src-tauri/src/`) — owns all logic: file validation, token generation, LAN selection, TLS, the Axum servers, and transfer state.
3. **Mobile browser pages** — HTML generated by the Rust server and served to the phone. No external assets, fonts, CDNs, or analytics.

### Frontend ↔ backend boundary
- The only contract is **Tauri commands** registered in `src-tauri/src/main.rs` (`invoke_handler`) and implemented in `commands.rs`. The TS-side mirror lives in `src/lib/api.ts` — when you add/change a command, update both sides plus the capability allowlist in `src-tauri/capabilities/default.json`.
- Rust emits **lifecycle events** (`approval_requested`, `download_started`, `progress_updated`, `download_completed`, `upload_*`, `shell_focus`, etc.). The frontend consumes them in `src/hooks/useTauriTransferEvents.ts` and **also polls** status (`useTransferPolling.ts`) as a fallback — keep both paths consistent.
- `App.tsx` is the single stateful container; everything in `src/components/` is presentational. Hooks in `src/hooks/` own event/polling/theme/speed logic.

### The two LAN listeners (security-critical, do not collapse)
When a transfer starts, the backend starts **two** servers:
- An **HTTPS Axum server** (rustls, `src-tauri/src/server/`) bound to the selected LAN IP. This is the only listener that receives app state and exposes token-bearing routes (`/d/:token`, `/download/:token`, `/u/:token`, `/upload/:token`, `/api/...`).
- A plain **HTTP listener** that serves *only* the generic `/connect` onboarding page and `/health`. It must never see a token.

The QR points at the HTTP `/connect` page with the real HTTPS URL placed **after `#`** (a URL fragment), so the token is never sent in the cleartext HTTP request. `/connect.js` validates the fragment is HTTPS, same host, explicit port, and a real `/d/` or `/u/` path before enabling navigation. **Preserve this fragment-handoff design** when touching onboarding or QR generation.

### TLS
Self-signed cert with the selected LAN IP as a SAN, generated via `rcgen` (`tls.rs`), persisted in the app config dir, and regenerated when the selected IP changes. It encrypts but does not authenticate — it cannot stop an active MITM. Don't claim otherwise in code or docs.

### Tokens & paths
- Tokens: 20 random bytes → unpadded base64url (160 bits entropy), in-memory only, single-use by default. No UUIDs/sequential IDs in URLs.
- **File paths never appear in URLs.** Selected paths are canonicalized at share creation and held in memory; transfer routes only accept tokens. This is what prevents path traversal — keep it that way.

### Transfer state lifecycle
The active share is a single `Option<ShareSession>` in memory (`state.rs`, `share.rs`). Statuses: `Ready`, `AwaitingApproval`, `Approved`, `Denied`, `Downloading`, `Completed`, `Expired`, `Cancelled`, `Error`. Approval has a hard 60-second deadline; a background Tokio task expires links. Receive mode mirrors this in `receive.rs`.

### Streaming
- Single files: Tokio async file I/O streamed from disk.
- Multi-file/folder: bounded-memory ZIP stream via `async_zip` (`archive.rs`), no temp archive.
- Uploads: stream into a randomized `.part` file in the destination, enforce the byte limit while streaming, verify name + final byte count match the approved metadata, fsync, then no-clobber persist. Incomplete temp files are removed on failure.

### Key backend modules
`commands.rs` (IPC entry points), `server.rs` + `server/{routes,download,upload,security,templates}.rs` (Axum + HTML), `archive.rs` (ZIP), `receive.rs` (upload mode), `tls.rs`, `network.rs` (LAN selection), `rate_limit.rs` (invalid-token rate limiting), `history.rs` (persisted transfer log), `settings.rs`, `shell_integration.rs` (right-click "Send" + global hotkey), `tray.rs` (close-to-tray).

### History
Terminal send/receive outcomes are copied into a bounded JSON log in the app config dir, keyed by session UUID to dedupe. Public Tauri responses carry display metadata only; source/destination paths stay backend-side and power "repeat", which validates paths and mints a fresh session/token.

## Conventions & constraints

- **Product scope is deliberately narrow** (PC↔phone, local Wi-Fi, no accounts/cloud/relay). Don't add cloud, accounts, or device-identity features without explicit direction.
- **No `unsafe`** unless genuinely required; if so, add a `SAFETY:` comment explaining the invariant. Keep public APIs explicit.
- **`cargo clippy` runs with `-D warnings`** — zero warnings.
- **Security headers** (`CSP`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`, `Cache-Control: no-store`, `Pragma: no-cache`) must be on every server response. Always sanitize filenames and HTML-escape values rendered into mobile pages.
- **Releases require version parity** across `package.json`, `src-tauri/tauri.conf.json`, and `src-tauri/Cargo.toml`; `npm run release:check` enforces it and CI runs it. See `docs/releasing.md`.
- Report security issues via private GitHub security advisory, not a public issue.
